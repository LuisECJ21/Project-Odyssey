-  TCP Necesita 4 datos para la comunicación:
    - Source IP    = 192.168.1.20
    - Source Port  = 53124
    - Destination IP   = 142.250.72.14
    - Destination Port = 443
- A esta combinación se le suele llamar TCP 4-Tuple.
- Ahora pensemos en un escenario donde se abre otra pestaña en el mismo explorador con otra conexión al mismo servidor o servicio https:
    - El stack de TCP es quien asigna el nuevo puerto efímero del origen para la comunicación, cuyo proceso se conoce como “demultiplexing”
    - Pero, para gestionar estas múltiples conexiónes el sistemas operativo asigna Sockets, que es el objeto/interfaz que el SO proporciona a una aplicación para que pueda comunicarse por la red.
- Para establecer la comunicación TCP:
    - El servicio de origen lleva información en los encabezados de la conexión TCP que quiere iniciar para intercambiar datos
    - El servidor responde, claro, si es que todo esta bien, con que esta listo para establecer la comunicación
    - Se requiere un tercer paso, para que el origen, confirme que recibió la respuesta del servidor.
    - A esto se le conoce como TCP Three-way handshake:
        - SYNC
        - SYNC/ACK
        - ACK
    - El ACK divide en secuencias, y si alguna secuencia falta, a pesar de que puede seguir recibiendo información, sigue pidiendo la que falta para su retransmisión, por ejemplo:

		Segmento 1
		SEQ = 1000
		500 bytes
		✓ recibido

		Segmento 2
		SEQ = 1500
		500 bytes
		✗ SE PIERDE

		Segmento 3
		SEQ = 2000
		500 bytes
		✓ recibido

    - 1500, porque aunque ta llegó el de 2000-2499 aún falta el de 1500 a 1999
- Pero se asume que el servidor y el cliente tienen la capacidad de recibir información sin un limite, pero no es asi, entonces que pasa? Se tiene un almacenamiento temporal, que es el bufer, mismo que no necesariamente es del mismo tamaño, y dependiendo de éste es que entre ellos se dirán, por ahora solo puedo recibir. 32KB o 64KB.
- Entonces, dado que el bufer no es eterno, se debe comunicar el tamaño del almacenamiento, o windows size, que de este mismo se deriva el concepto de Receive Windows (rwnd)
- SEQ     → ¿Dónde pertenecen estos bytes?
- ACK     → ¿Hasta dónde he recibido consecutivamente?
- Window  → ¿Cuánto más puedo recibir?
- Si yo fuera el emisor y recibo, windows=0 entra en control de flujo, la conexión sigue existiendo pero, se deja de enviar información, cuando se libera espacio y se comunica esto, al emisor o receptor, la comunicación se reanuda.
- Si no hay temas de espacio en bufer, pero hay señales de congestión (cwnd), TCP, existe un control de congestión, y empieza a enviar menos inflamación para dejar de congestionar.
Si tenemos lo siguiente:

rwnd = 10,000
cwnd =  3,000

- Hay algoritmos de control de congestión, y uno ellos es slow start y hace referencia a medir o explorar cuantos datos se pueden pueden tener en “vuelo”, aumentando progresivamente en función de los ACK, hasta que de señales de congestión
- Tambien en este caso entra el RTT (Round Trip Time) que es el tiempo que toma desde que se hace la petición hasta que se confirma regresa la respuesta de confirmación, este influye en proceso de retransmisión, por ejemplo, si una respuesta tarda por lo general 40 ms de RTT, y ya pasaron por ejemplo 100 ms, es casi un hecho que el paquete se perdió, ese limite se llama RTO (Retransmisión TimeOut), si el tiempo de respuesta lo excede, retransmite el paquete.
- TCP calcula el RTO en función del contexto anterior.
    - Si quiza solo el paquete aun no se habia entregado y se retransmite, a través de información como la SEQ que espera, se puede dar cuenta y no entregarlos dos veces a la aplicación
- Ahora, como muere una conexión? —> TCP tiene la bandera FIN para decir ya terminé de enviar datos, pero no libera todo los recursos de forma inmediata, porque? Si el cliente ya termino de enviar datos, no necesariamente el servidor también, y lo controla con TIME_WAIT para evitar por ejemplo, confundir trafico viejo, con el nuevo.
